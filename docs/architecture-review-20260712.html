Problema

O módulo PageContext expõe dois caminhos para obter uma sessão: ctx.session (opcional, None em rotas públicas) e ctx.new_session() (abre uma nova). Views precisam saber se estão em rota pública ou autenticada e bifurcar o código. Isto vaza a decisão de lifecycle do framework para cada view.

Solução

_build_and_invoke sempre abre uma sessão, inclusive para rotas públicas. PageContext.session nunca é None. Remove _session_factory e new_session() — views que precisam refrescar o estado após mutação podem fazê-lo dentro da mesma sessão ou com session.refresh.

Ganhos

  • locality: toda decisão de sessão fica em app.py — views nunca abrem sessão
  • leverage: 10 views deixam de bifurcar; interface do PageContext encolhe de 4 campos para 3
  • testabilidade: testes de view recebem uma sessão real sem precisar mockar factory

Problema

O módulo é raso: a interface (474 linhas de view misturada com estado) é quase tão larga quanto a implementação. 7 variáveis nonlocal em closures impedem testes unitários do comportamento de seleção/filtro sem renderizar UI. Bugs de toggle de tag e refresh de entries estão no mesmo espaço de nomes que padding e ícones.

Solução

Extrair ExploreState (dataclass com selected_category_id, expanded_ids, selected_tags, is_searching) e FeedBrowser (módulo de domínio com async load(), select_category(), toggle_tag(), search()). A view vira um renderizador puro que recebe o estado e retorna ft.View.

Ganhos

  • locality: regras de filtro e busca concentram em um módulo de domínio
  • testabilidade: FeedBrowser testável sem Flet — só asserts em estado
  • profundidade: interface do módulo de domínio tem 4 métodos; implementação tem 474 linhas de lógica real

Problema

FeedFetcher ABC tem interface de 1 método (fetch()) — quase tão larga quanto a implementação (HttpFeedFetcher.fetch() + parsing). O módulo é raso. A interseção real (substituir HTTP por in-memory em testes) está no nível do cliente HTTP, não no nível do feed já parseado. Tests usam FakeFeedFetcher em vez de mockar o HTTP, o que significa que parsing não é testado.

Solução

Eliminar o ABC. refresh_single_feed aceita httpx.AsyncClient | None como parâmetro de interseção. Parsing (_parse_entry) é inlinado ou mantido como função interna. Tests passam um AsyncClient mockado que retorna XML bruto — testando parsing e refresh juntos.

Ganhos

  • profundidade: refresh_single_feed vira módulo profundo — parsing + HTTP + persistência em uma interface de 2 parâmetros
  • locality: lógica de refresh e parsing no mesmo módulo — não saltar entre dois arquivos
  • testes: XML malformado, encoding, HTTP 304, redirect — tudo testável via mock HTTP
⚠️ Contradiz parcialmente o ADR-0001 (que justifica PostgreSQL sobre SQLite por tsvector). O ADR não cobre fetch — sem conflito direto.

Problema

get_category_tree mistura queries SQL com lógica de rollup (feed_count, unread_count, children recursivos). O resultado é um dict aninhado que views consomem como está — mas category_list_view precisa de _flatten_tree_for_dropdown (escrito na view) porque o formato do dict não encaixa exatamente. A lógica de rollup está no service (DB layer), mas é lógica de domínio (como contar não-lidos em subcategorias).

Solução

Separar: get_categories_with_counts(session, user_id) retorna dados planos (categorias + feed_count + unread_count). Uma função pura build_tree(cats, feed_counts, unread_counts) constrói o dict aninhado. Views podem chamar build_tree com os mesmos dados ou transformar para seus formatos específicos.

Ganhos

  • locality: rollup não está trancado no service — views podem re-compor
  • testabilidade: build_tree é pura: dados de entrada, dict de saída, sem DB
  • profundidade: build_tree tem interface pequena (4 listas planas) e implementação recursiva complexa

Recomendação principal

Sessão inconsistente — dois caminhos para a mesma dependência

É o candidato com maior alavancagem: afeta todas as 10 views, elimina uma bifurcação que toda view precisa entender, e remove a capacidade de views abrirem sessões próprias — o que hoje leva a padrões inconsistentes (algumas views usam ctx.session, outras abrem new_session(), outras fazem ambos). A correção é localizada (só app.py e context.py) e o ganho se espalha por todo o codebase.

Segundo: explorar o colapso de estado da explore_view — o maior ponto de atrito para navegação por IA e o maior risco de regressão em mudanças de UI.
